# Data Classes — Entities & dart_mappable

These rules define how domain entities and data classes must be structured across both `dab_api` and `dab_app`. The project uses **dart_mappable** exclusively for serialization. Manual `toJson`/`fromJson` is forbidden.

---

## 🏗️ Anatomy of an Entity

Every domain entity follows this exact structure:

```dart
import 'package:dart_mappable/dart_mappable.dart';

part 'activity.mapper.dart'; // ← always the very first part directive

/// [ARCH: DOMAIN_ENTITY]
/// ROLE: <what this entity represents in the business domain>
/// CONTRACT: Immutable Plain Old Data (POD) object.
/// CONSTRAINTS: Must be serializable via [ActivityMappable].
@MappableClass()
class Activity with ActivityMappable {
  final String id;
  final ActivityProvider provider;
  final String title;

  Activity({
    required this.id,
    required this.provider,
    required this.title,
  });
}

// Domain extensions co-located in the same file, below the class
extension OnActivity on Activity {
  ActivityCategory get type => provider.category;
}
```

### Required patterns for every entity:
1. `@MappableClass()` annotation on the class.
2. `with [ClassName]Mappable` mixin on the class.
3. `part '[filename].mapper.dart';` directive at the top.
4. `[ARCH: LAYER_NAME]` annotation in the doc-comment.
5. All fields must be `final`.

---

## 🔒 Immutability Rules

- **All entity fields are `final`** — never `var` or non-final.
- Use `copyWith` (generated by `dart_mappable`) for mutations. Never manually create a partially updated entity.
- **No business logic inside entities.** Only getters and pure transformations via extensions.

```dart
// ✅ Correct — use generated copyWith
final updated = user.copyWith(name: 'New Name');

// ❌ Wrong — mutating fields is not possible (final), and manual mutation is forbidden
user.name = 'New Name'; // compilation error
```

---

## 📦 Sealed Classes & Enums

Use `sealed class` for discriminated unions (e.g., `AppFailure`, `ActivityProvider`). Each subclass is in the **same file** and annotated with `@MappableClass()`.

```dart
@MappableClass()
sealed class AppFailure with AppFailureMappable {
  final String message;
  const AppFailure(this.message);
}

@MappableClass()
class ServerFailure extends AppFailure with ServerFailureMappable {
  final int? statusCode;
  const ServerFailure({required String message, this.statusCode}) : super(message);
}
```

Use `@MappableEnum()` for enums that must be serialized:

```dart
@MappableEnum()
enum ActivityCategory { commit, revision, task, generic }
```

## 🗺️ Entity-to-Model Mapping (Infrastructure layer)

In the App, remote JSON responses are mapped to domain entities using `dart_mappable`'s generated mappers — not manual `fromJson` factories. The mapping always lives in the **infrastructure layer**, never in the entity itself.

```dart
// ✅ Correct — in repository or datasource
final activity = ActivityMapper.fromMap(jsonMap);

// ❌ Wrong — entity should not know about raw JSON parsing
Activity.fromJson(json);  // forbidden — do not add this factory manually
```

---

## 🚫 What Not to Do

- **Never use `json_serializable`** (`@JsonSerializable`). The project uses `dart_mappable` exclusively.
- **Never write `toJson()` or `fromJson()` manually** on any entity. Run `build_runner` instead.
- **Never edit `*.mapper.dart` files** — they are 100% generated. All changes go into the source entity file.
- **Never add non-final fields** to an entity class.
- **Never place networking or persistence logic** inside an entity (no `Dio`, `ObjectBox`, `Box`, etc.).
- **Never combine two different classes or enums in the same file.** The only exception is for `sealed class` hierarchies where all subclasses may stay in the same file.
- Unrelated enums used by a class must live in their own file (e.g., `user_role.dart` instead of being inside `user.dart`).

## 📂 Folder-Based Subject Grouping

To maintain organization under the "one-class-per-file" rule, related data classes must be grouped into subdirectories based on their business subject.

### Required Pattern for Presentation Models:
1. **Feature-Local Models**: Data classes specifically for one view belong in `lib/presentation/views/[feature]/models/`.
2. **Shared UI models**: Generic UI models (like `ViewStatus`) belong in `lib/presentation/core/models/`.
3. **One Model per File**: Each enum or data class must have its own file, satisfying the `@MappableClass` requirements.
1. **Mandatory for Entities**: In both `dab_api` and `dab_app`, the `domain/entities/` folder must use subject-based subdirectories (e.g., `user/`, `activity/`, `group/`) whenever more than one file relates to that subject.
2. **Subject Consistency & Prefixing**: Files within a subject folder **must** share a common prefix matching the folder name (e.g., `user.dart`, `user_role.dart`, `user_identity.dart` in `entities/user/`). If a related class disappears from this naming scheme (e.g., `sprint_context.dart`), it must remain in the root `entities/` folder even if logically related to the subject.
3. **Exclusion (Events & States)**: This grouping rule does **not** apply to Bloc/Cubit `Events` or `States`. These should remain co-located with their respective logic components as per standard feature-folder patterns.

## 🔄 After Modifying Entities

Always regenerate code after any change to a `@MappableClass` or `@MappableEnum`:

```bash
# API
dart run build_runner build --delete-conflicting-outputs

# App
dart run build_runner build --delete-conflicting-outputs
```
